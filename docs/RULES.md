# GoldenMatch Pro — Бизнес-правила и ограничения

> Жёсткие правила, которые должны соблюдаться во всём коде и архитектуре.
> Нарушение любого из этих правил = баг.

---

## 1. Matching: ключи и приоритеты

### Part Number — главный ключ
- Part number — единственный надёжный идентификатор электронного компонента
- Exact match по нормализованному PN = автоматический матч (при score ≥ 0.92)
- Fuzzy matching по описанию — только fallback, вес не более 5%
- Никогда не принимать решение только по описанию без PN или параметров

### Нормализация Part Number
- Uppercase: `cm1000e3u-34nf` → `CM1000E3U-34NF`
- Удалять пробелы: `6ES7 321-1BL00-0AA0` → `6ES7321-1BL00-0AA0`
- Слэши → дефисы: `SKKT162/16E` → `SKKT162-16E`
- Стрипать packaging suffixes: `-ND`, `-TR`, `-CT`, `-NOPB`, `-PBF`
- Разные ревизии (-1 vs -2) — это РАЗНЫЕ компоненты, не стрипать

### Manufacturer — второй ключ
- Один PN от разных MFR = разные компоненты
- Всегда проверять пару (PN + manufacturer)
- Русские написания обязательны: "Сименс" → Siemens

### Три сценария
- **A** (есть PN): exact match, не fuzzy
- **B** (категория + параметры): blocking по категории, scoring по params
- **C** (только описание): широкий матч, помечать "manual review"

## 2. Splink: пороги

| Вероятность | Решение | Действие |
|-------------|---------|----------|
| ≥ 0.92 | `auto` | В дашборд как подтверждённый |
| 0.75–0.91 | `borderline` | В LLM-judge |
| < 0.75 | `reject` | Отбрасываем |

- При калибровке: precision > recall

## 3. LLM-judge

### Когда вызывается
- Только borderline 0.75–0.92
- Никогда для auto (≥0.92) и reject (<0.75)

### Fallback
- Таймаут 5 сек → ручная очередь
- Невалидный JSON → ручная очередь
- API недоступен → ручная очередь
- Пайплайн никогда не ломается из-за LLM

### Стоимость
- ~0.3–0.7 ₽/вызов, ~50–100 ₽/день при 50 тендерах

## 4. Relevance ranking

```
relevance = match_quality × 0.40
           + stock_availability × 0.25
           + margin_estimate × 0.20
           + deadline_urgency × 0.15
```

### Stock: `min(qty / 50, 1.0)`, 0 если нет на складе
### Margin: НМЦ >100K → 1.0, 50–100K → 0.6, <50K → 0.25
### Deadline: ≤5d → 1.0, 6–10d → 0.67, 11–20d → 0.33, >20d → 0.13

## 7. Product invariants (поведенческие, движок-независимые)

Три инварианта, проверяемых tests/test_pipeline_e2e.py.
Нарушение любого = баг, независимо от того, какой движок 
(fallback / Splink) активен.

| # | Инвариант | Тест | Связь с правилами |
|---|-----------|------|-------------------|
| 1 | Тендер с точным PN из каталога → auto-decision | test_happy_path_exact_pn_routes_to_auto | §1 (PN — главный ключ) |
| 2 | Тендер без связи с каталогом → не auto | test_garbage_tender_never_routes_to_auto | §2 (precision > recall) |
| 3 | Параметрический матч (Сценарий B) → не auto | test_parametric_match_never_routes_to_auto | §1, §3 (LLM только для borderline) |

Эти инварианты не зависят от:
- Текущей probability на fallback-скоринге
- Установлен ли Splink
- Конкретных весов в splink_config.py
- Точного количества матчей в результатах

При смене движка тесты не переписываются. Если они краснеют после
смены — либо нарушен контракт продукта (правим продакшн-код),
либо тест был написан как «факт», а не «инвариант» (правим тест).
